## 4. 🔍 원인 분석 (WWDC25 기준)

### 4.1 긴 View Body 업데이트

> **WWDC25**: View Body가 프레임 데드라인을 초과하면 히치가 발생합니다.


#### 🟡 LivithMainTabView

- **최대 실행 시간**: 6.79ms
- **위험도**: 프레임 예산 25% 초과 - 주의 필요

**가능한 원인**:
- View Body 내에서 Formatter(NumberFormatter, DateFormatter) 생성
- 복잡한 계산 속성(computed property) 호출
- 동기적 데이터 변환/파싱 작업

**해결 방안 (WWDC25 권장)**:
1. 비싼 작업을 View Body 외부로 이동 (LocationFinder 패턴)
2. Formatter를 한 번 생성하여 재사용 (캐싱)
3. 계산 결과를 미리 캐시하고 View는 캐시된 값만 읽기
4. 백그라운드에서 처리 후 메인 스레드에서 UI 업데이트

### 4.2 Observable 종속성 문제 의심

> **WWDC25**: @Observable의 광범위한 종속성은 불필요한 업데이트를 유발합니다.


#### ⚠️ Button

- **업데이트 횟수**: 3516회
- **평균 실행 시간**: 7.69µs

**가능한 원인**:
- 전체 배열/딕셔너리에 대한 종속성 (개별 요소가 아닌)
- @Observable 클래스의 모든 속성에 대한 광범위한 종속성
- 하나의 상태 변경이 관련 없는 여러 View를 업데이트

**해결 방안 (WWDC25 권장)**:
1. 각 View에 대한 개별 ViewModel 생성 (세분화된 종속성)
2. favorites 배열 전체가 아닌, 개별 항목의 isFavorite 속성에 종속
3. Equatable conformance로 실제 변경된 경우만 업데이트

## 6. 📚 WWDC25 SwiftUI 성능 핵심 원칙

### View Body 속도 유지
- 60fps 기준 각 View Body는 **16.67ms** 이내 완료 권장
- 비싼 작업(Formatter 생성, 복잡한 계산)은 View Body 외부에서 수행

### 불필요한 업데이트 방지
- @Observable의 세분화된 종속성 설계
- 전체 컬렉션이 아닌 개별 항목에 대한 종속성 사용
- Equatable conformance로 실제 변경 시에만 업데이트

### 데이터 흐름 설계
- 각 View가 필요한 데이터에만 종속되도록 설계
- ViewModel을 통한 데이터 캡슐화
- Environment에 자주 변경되는 값 저장 피하기
