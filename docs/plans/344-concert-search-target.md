# [#344] 공통 공연 검색 타깃 연결 계획

## 배경

일반 검색, 관심 콘서트 설정·변경, 인스타그램 수동 공연 검색이 모두 `SearchRepository`로 공연을 조회해요. 첫 페이지 조회, 결과 추가, 진행 중인 요청의 교체를 각자 처리합니다. 공유 검색 로직은 `Projects/Shared`의 기존 Tuist 프로젝트 안에 전용 프레임워크 타깃으로 둡니다. [상태 소유권 ADR 0002](../adr/0002-viewmodel-ownership.md)

## 목표

- `HomeFeature`와 `SearchFeature`가 검색 전용 타깃에 각각 의존합니다. 검색 타깃의 앱 내부 의존성은 `Domain`으로 두고, 각 화면 모델이 기존 경로에서 받은 `SearchRepository`를 전달합니다.
- 각 화면은 검색 모델 인스턴스를 하나씩 소유합니다. 공통 모델은 확정된 조회 조건, 결과, 커서, 첫 페이지·추가 페이지 로딩, 요청 취소와 응답 유효성을 관리합니다. 첫 페이지는 결과를 교체하고, 다음 페이지는 해당 결과를 만든 조건으로만 요청합니다.
- 새 조회로 교체되거나 무효화된 요청의 성공·실패가 현재 결과, 오류 표시, 로딩 상태를 덮지 않습니다. 마지막 카드가 반복해서 나타나도 같은 추가 페이지 요청은 진행 중에 한 번만 실행됩니다.
- 검색 시작과 초기화 시점, 오류 표시, 기본 카탈로그, 공연 선택·저장·등록, 화면 이동은 각 화면의 책임입니다.

## 권한·범위

- 합의한 배치 · `Projects/Shared` 안의 검색 전용 프레임워크 타깃.
- 연결 범위 · `InterestConcertSettingViewModel`, `InstagramManualSearchViewModel`, 일반 검색 `SearchView`. 일반 검색의 `SearchStore`는 화면이 소유하는 `@MainActor @Observable` ViewModel로 전환합니다.
- `ExploreStore`의 일반 탐색, 인스타그램 매칭 후보 확인, 관심 공연 목록 전용 화면은 이번 연결 대상에서 제외합니다. Repository 계약과 요청 API도 이번 변경 범위 밖입니다.
- [GitHub 이슈 #344](https://github.com/mediunn/Livith-iOS/issues/344)

## 작업 항목

1. **변경 전 기준 확인.** `InterestConcertSettingViewModelTests`, `InstagramManualSearchViewModelTests`, `SearchStoreTests`를 실행합니다. 기존 테스트가 직접 다루지 않는 화면 동작은 아래 수동 시나리오로 확인합니다. 실패가 있으면 기준 커밋의 결과로 기록합니다.
2. **Shared 타깃을 만들고 관심 콘서트 설정부터 연결.** 기존 `Shared` 매니페스트와 타깃 매핑에 프레임워크를 추가하고 `HomeFeature`에서 참조합니다. 설정 화면으로 첫 검색, 추가 페이지, 검색어 삭제, 기본 목록 복원, 검색 페이지의 공연 정보 보관까지 확인합니다. 검색 API 오류는 기존 토스트 경로로 전달합니다. 여기서 공통 모델과 화면 사이에 필요한 데이터가 무엇인지 검증합니다.
3. **인스타그램 수동 검색 연결.** `HomeFeature`의 같은 의존성을 사용합니다. 정규화한 검색어가 바뀔 때 동작하는 `.task(id:)`, 이미 처리한 검색의 재실행 방지, 선택 ID 유지, 등록 작업의 수명을 확인합니다. 두 Home 화면의 테스트를 함께 실행해 한쪽의 변경으로 다른 쪽 상태나 요청이 달라지지 않는지 확인합니다.
4. **일반 검색을 ViewModel로 바꾸고 마지막에 연결.** `SearchFeature`에서 같은 타깃을 참조합니다. 새 `SearchViewModel`이 필터·정렬과 조회 시작을 조정하고, `SearchView`는 화면 모델을 소유합니다. 결과 배열과 커서는 공통 모델이 소유합니다. 기존 결과 유지, 추가 페이지 재시도, 첫 페이지와 추가 페이지의 표시 차이를 보존합니다.
5. **세 화면 통합 확인.** 공통 모델과 연결 화면의 관련 테스트를 실행한 뒤 Dev 앱 빌드와 시뮬레이터 수동 확인을 진행합니다. 세 화면별 명령, 실행 건수, 수동 확인 결과를 남깁니다.

## 영향 범위

| 타깃 | 변경 내용 |
|---|---|
| `Shared`의 검색 전용 타깃 | 조회 조건에 해당하는 상태, 페이지 처리, 취소 처리. 화면이 판단할 수 있도록 수락한 페이지와 오류를 전달하는 경계. |
| `HomeFeature` | 의존성 한 곳 추가. 관심 콘서트 설정과 수동 검색의 검색 결과 조회를 교체. 별도 카탈로그와 화면별 저장·등록은 해당 화면 모델이 담당. |
| `SearchFeature` | 의존성 한 곳 추가. 일반 검색 Store를 ViewModel로 전환하고 `SearchView`의 목록·로딩을 연결. |

## 기술 결정

| 선택 사항 | 결정·근거 | 확인 상태 |
|---|---|---|
| 타깃 배치 | 기존 `Projects/Shared/Project.swift`에 검색 전용 프레임워크를 둡니다. | 사용자 합의 |
| 연결 순서 | 설정 → 수동 검색 → 일반 검색. 같은 API 조건과 그리드를 쓰는 두 화면으로 경계를 검증한 뒤, 다른 오류 정책과 표시 방식을 가진 일반 검색을 ViewModel로 전환하면서 연결합니다. | 계획안 |
| 호출 경계 | 화면이 `Criteria`와 실패 정책을 전달합니다. `ConcertSearchViewModel`의 `search`, `loadNextPage`, `invalidateSearch`, `reset`으로 조회를 조정해요. 수락한 페이지와 오류는 조회 완료 콜백으로 전달합니다. | 구현 반영 |

## 주의 사항

- 두 Home 화면은 입력이 바뀌는 순간 이전 검색 페이지를 무효화하고, 검색어를 비우면 기본 카탈로그와 기존 카탈로그 커서를 복원합니다. 일반 검색은 새 입력이 아직 조회되지 않은 동안 기존 검색어로 추가 페이지를 이어갈 수 있고, 검색어를 비우면 현재 필터·정렬로 다시 조회합니다.
- 검색 실패 후 일반 검색은 표시 중인 결과를 유지하고 추가 페이지 실패 때 기존 커서를 보존합니다. 두 Home 화면은 검색 결과와 검색 커서를 비웁니다. 관심 콘서트 설정의 **기본 카탈로그** 추가 페이지 오류는 기존 카탈로그를 유지합니다.
- 일반 검색의 기존 300ms 검색 대기와 500ms 추가 페이지 대기는 화면이 시작 시점을 결정합니다. 수동 검색의 `.task(id:)` 취소가 내부 조회에도 전달되고, 등록 요청은 등록용 수명을 따르는지 구분해 확인합니다.
- 일반 검색을 Observation으로 전환한 뒤 결과·로딩 변경이 SwiftUI에서 실제로 갱신되는지 확인합니다. 자동 테스트의 요청 처리 결과와 화면 표시 결과를 각각 기록합니다.

## 인수인계

변경 전후를 가르는 핵심 시나리오는 **다음 페이지를 기다리는 동안 검색어를 지우는 경우**입니다. 두 Home 화면은 즉시 기존 카탈로그를 보여주고, 일반 검색은 현재 필터로 빈 검색어의 첫 페이지를 엽니다. 이전 검색의 성공과 실패를 늦게 반환시켜 결과, 오류, 로딩이 뒤집히지 않는지 확인합니다.

### 변경 전 기준

`4d302ccd`의 iPhone 17 iOS 26.5 시뮬레이터에서 Home의 두 ViewModel 스위트 35개와 기존 `SearchStoreTests` 3개가 통과했습니다. Home은 매개변수 조합을 포함하면 37건을 실행했습니다.

### 변경 후 검증 환경

같은 iPhone 17 iOS 26.5에서 세 스킴의 `.xcresult`를 확인했습니다. 총 42개 테스트가 통과했고, 매개변수 조합을 포함하면 45건입니다. 현재 Tuist CLI의 `build` 하위 명령은 빌드 정보 조회용이라 Dev 앱 컴파일은 `xcodebuild build`로 실행했습니다. Dev 앱을 별도 시뮬레이터에 설치해 로그인 화면을 확인했고, 검색 화면 조작에는 로그인 세션이 필요합니다.
