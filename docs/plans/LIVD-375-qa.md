# LIVD-375 QA 브랜치 운영 계획

## 배경
- QA 반영 작업을 현재 브랜치에서 직접 진행하지 않고, 별도 서브 브랜치에서 수행하려고 한다.
- 현재 브랜치에는 불필요한 머지 커밋을 만들지 않고, 서브 브랜치의 커밋 흐름을 선형으로 반영해야 한다.
- QA 작업 커밋은 하나로 모으지 않아도 되며, 작업 과정의 커밋을 그대로 유지한다.
- 프로젝트 기본 규칙은 작업 브랜치를 `develop`에서 분기하는 것이지만, 이번 QA 서브 브랜치는 현재 작업 브랜치 보존을 위한 운영 예외로 둔다.

## 목표
- 현재 브랜치 `fix/LIVD-375-qa`는 QA 반영 기준 브랜치로 유지한다.
- 실제 QA 수정 작업은 서브 브랜치에서만 수행한다.
- 서브 브랜치 작업 완료 후 현재 브랜치에는 `git merge --ff-only`로 선형 히스토리만 반영한다.
- 현재 브랜치가 서브 브랜치와 다른 방향으로 분기된 경우 fast-forward 반영이 실패하도록 하여 잘못된 머지를 방지한다.
- 최종 PR 대상은 기존 현재 브랜치 `fix/LIVD-375-qa`로 유지한다.

## 작업 항목
- [ ] 현재 브랜치 상태 확인
  - `git status --short --branch`로 현재 브랜치와 워킹트리 상태를 확인한다.
  - 현재 브랜치가 `fix/LIVD-375-qa`인지 확인한다.
  - QA 서브 브랜치를 만들기 전 워킹트리가 clean인지 확인한다.
  - 계획 문서 변경이 남아 있다면 QA 작업과 섞이지 않도록 먼저 별도 승인/커밋하거나 의도적으로 제외한다.
- [ ] 서브 브랜치 생성
  - 현재 브랜치에서 QA 작업용 서브 브랜치를 생성한다.
  - 브랜치 이름은 `fix/LIVD-375-qa-login`처럼 `fix/LIVD-375-qa-간략한-영문-설명` 형태로 작성한다.
- [ ] 서브 브랜치에서 QA 수정 작업 및 커밋
  - QA 수정은 서브 브랜치에서만 수행한다.
  - 커밋은 작업 단위에 맞게 여러 개로 나누어도 된다.
  - 커밋 전 `git diff`로 변경 내용을 확인한다.
  - 커밋은 사용자에게 명시적으로 승인받은 뒤 수행한다.
  - 커밋 메시지는 `docs/rules/git.md`의 `[Type] 이슈키 - 변경 내용 요약` 형식을 따른다.
- [ ] 현재 브랜치 변경 여부 확인
  - 현재 브랜치로 돌아가기 전에 서브 브랜치 변경 사항이 모두 커밋되었는지 확인한다.
  - 현재 브랜치로 이동한 뒤 별도 커밋이 생기지 않았는지 확인한다.
- [ ] 현재 브랜치에 fast-forward 반영
  - 현재 브랜치에서 `git merge --ff-only <서브브랜치>`를 실행한다.
  - `--ff-only`가 실패하면 현재 브랜치와 서브 브랜치가 서로 다른 분기로 진행된 상태로 판단한다.
- [ ] 최종 상태 확인
  - `git status --short --branch`로 워킹트리가 깨끗한지 확인한다.
  - `git log --oneline --decorate --graph`로 머지 커밋 없이 선형 히스토리인지 확인한다.

## 주의 사항
- 현재 브랜치 기반 서브 브랜치는 이번 QA 운영을 위한 예외이며, 일반 신규 작업 브랜치에는 `develop` 분기 규칙을 적용한다.
- 현재 브랜치 `fix/LIVD-375-qa`에서는 직접 QA 수정 커밋을 만들지 않는다.
- QA 서브 브랜치 생성 전 워킹트리가 clean하지 않으면 계획 문서 변경과 QA 변경이 섞일 수 있다.
- 커밋, amend, push, force push는 `docs/rules/git.md`에 따라 사용자에게 명시적으로 승인받은 뒤 수행한다.
- 서브 브랜치 작업 중 현재 브랜치에 별도 커밋이 생기면 `git merge --ff-only`는 실패한다.
- `git pull`은 원격 변경을 가져와 merge 또는 rebase까지 수행할 수 있으므로, 현재 브랜치 반영 목적의 기본 명령으로 사용하지 않는다.
- 원격 서브 브랜치를 반영해야 할 때는 `git fetch origin` 후 `git merge --ff-only origin/<서브브랜치>`를 사용한다.
- fast-forward 실패 시 일반 merge로 전환하지 않고, 현재 브랜치에 생긴 커밋과 서브 브랜치 기준점을 먼저 확인한다.
- 충돌이 필요한 상황이면 서브 브랜치를 현재 브랜치 위로 `rebase`한 뒤 현재 브랜치에서 다시 fast-forward 반영한다.

## 검증 방법
- 작업 전후 `git status --short --branch`로 브랜치와 워킹트리 상태를 확인한다.
- 서브 브랜치 작업 완료 후 현재 브랜치에서 `git merge --ff-only <서브브랜치>`가 성공하는지 확인한다.
- `git log --oneline --decorate --graph`에서 현재 브랜치 히스토리가 머지 커밋 없이 한 줄로 이어지는지 확인한다.
- fast-forward 실패 시 `git log --oneline --decorate --graph --all`로 분기 지점을 확인한다.
