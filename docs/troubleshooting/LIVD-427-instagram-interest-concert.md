# [LIVD-427] 인스타그램 공유 → 관심 콘서트 등록 화면 구현 - 트러블슈팅

## 기록

### 2026-07-09 - 디자인 정밀 대조 미흡 피드백 → design context 기반 재대조

**상황**
- 사용자가 디자인을 제대로 보고 반영하라고 지적했다. 초기 구현은 메타데이터(좌표)와 일부 스크린샷 기준이었고, 화면별 design context(폰트·색·간격 스펙)를 전수 대조하지 않았다.

**문제**
- 재대조 결과 3건 불일치: ① "직접 찾아볼게요" 폰트가 Body2-md(16 Medium)인데 body3Medium(15)로 구현, ② 취소 버튼이 black80 배경+black30 텍스트인데 LivithButton .secondary(black50 배경+white 텍스트) 사용, ③ FR-05 타이틀 상단 패딩이 20인데 30으로 구현.

**원인**
- 파이프라인 규칙("Figma 재대조 차이 0건 수렴")을 View 수작업 구현에는 적용하지 않고 구조 수준 대조로 끝냈다.

**해결**
- 화면별 get_design_context로 스펙을 뽑아 전수 대조 후 3건 수정. 취소 버튼은 디자인에 대응하는 variant가 없어 `LivithButtonVariant.cancel`(black80/black30, pressed black90)을 DesignSystem에 추가했다.
- 잔여 차이 1건(범위 외로 보고): LivithButton 전역 비활성 스타일(black80 배경/black50 텍스트)이 디자인의 비활성(black50 배경/black30 텍스트)과 다름 — 기존 화면 전체에 영향이라 별도 디자인시스템 이슈로 분리 필요.

**교훈**
- 신규 화면은 코드 작성 전에 화면별 design context를 뽑아 폰트·색·간격 스펙 표를 만들고, 구현 후 그 표로 재대조한다. 스크린샷·메타데이터만으로는 폰트 크기와 컴포넌트 variant를 구분할 수 없다.

### 2026-07-09 - 매칭실패 화면 헤더 구성 오류 피드백 (뒤로가기/정보 요청 버튼)

**상황**
- FR-05 두 화면(매칭실패/직접찾기) 모두 `LivithNavigationView .back`(뒤로가기+타이틀)으로 구현했다.

**문제**
- 사용자가 매칭실패 화면에는 뒤로가기가 없어야 하고 정보 요청 버튼이 있어야 한다고 지적했다. Figma 헤더 노드를 대조하니 매칭실패는 뒤로가기 없이 우측 "정보 요청" 버튼만, 직접찾기는 뒤로가기 + 정보 요청 버튼 구성이었다.

**원인**
- 화면 전체 스크린샷만 보고 헤더 구성을 두 화면 동일하다고 가정했다. 헤더 컴포넌트 노드(진입 경로별 차이)를 개별 대조하지 않았고, FR-06 관련 요소를 후속 이슈로 빼면서 정보 요청 "버튼 노출"까지 함께 제외했다.

**해결**
- 커스텀 헤더로 교체: 매칭실패는 우측 `LivithReportButton("정보 요청", variant: .info)`만, 직접찾기는 좌측 뒤로가기 + 우측 정보 요청 버튼. 버튼 탭 액션(FR-06_요청 페이지)은 페이지 디자인이 없어 후속 이슈로 유지(TODO).

**교훈**
- 같은 레이아웃을 공유하는 화면 변형이라도 헤더·네비게이션 구성은 노드 단위로 개별 대조한다. 범위에서 화면을 제외할 때 그 화면에 붙은 진입점(버튼)까지 제외되는지 확인한다.

### 2026-07-08 12:30 - Figma 재접속 후 확정 문구 반영

**상황**
- 임시 문구로 구현했던 성공·실패 토스트, 중단 팝업 문구를 Figma 재수집으로 확정하고자 했다.

**문제**
- 임시 문구가 Figma 실제 카피와 달랐다. 성공 토스트는 "[콘서트명] 관심 콘서트로 등록되었어요"가 아니라 매칭 화면(FR-04)은 "[콘서트명 20자 말줄임].. 콘서트가\n관심 콘서트와 일정에 자동 등록되었어요", 검색 화면(FR-05)은 "관심콘서트와 일정에 등록했어요"로 서로 달랐다. 실패 토스트는 "관심 콘서트 등록에 실패했어요\n다시 시도해주세요", 중단 팝업은 "관심 콘서트 등록을 그만 두시나요?\n관심 콘서트에서 다시 지정할 수 있어요."였다.

**원인**
- 임시 문구 지정 시 두 화면의 성공 토스트가 다르다는 점과 콘서트명 20자 말줄임 규칙(FR-04 명세 4번)을 반영하지 못했다.

**해결**
- 문구 변경을 red 테스트로 먼저 확인(6건 실패)한 뒤 Store 상수·View 리터럴을 확정 문구로 교체하고 green(22건) 확인했다. 콘서트명 20자 초과 시 `prefix(20)..` 말줄임 테스트를 추가했다.

**교훈**
- 같은 성격의 토스트라도 화면마다 카피가 다를 수 있으니 화면별로 Figma 원본을 확인한다. Figma 활성 탭이 대상 문서일 때 필요한 노드를 한 번에 수집한다.

### 2026-07-08 12:05 - HomeFeature 전체 테스트에서 선행 실패 1건 발견

**상황**
- 신규 Store 구현 후 회귀 확인을 위해 HomeFeature scheme 전체 테스트(84개)를 실행했다.

**문제**
- `HomeStoreTests`의 "관심 콘서트 정리 정책별 성공 메시지를 설정해야 한다" 테스트 1건이 실패했다. 프로덕션 문구는 "종료·취소된 공연이 자동 정리됐어요", 테스트 기대값은 "취소·종료된 공연이 자동 정리됐어요"로 어순이 불일치한다.

**원인**
- develop 시점부터 존재하던 문구·기대값 불일치. 이번 브랜치는 `HomeStore.swift`와 `HomeStoreTests.swift`를 변경하지 않았다 (git diff로 확인).

**해결**
- 미해결. 이슈와 무관한 변경을 브랜치에 섞지 않기 위해 수정하지 않고 보고만 남긴다. 별도 이슈로 처리 필요.

**교훈**
- 전체 스위트 실패가 나오면 브랜치 diff와 대조해 선행 실패인지 먼저 판별한다.

### 2026-07-08 11:40 - Figma 문서 탭 비활성화로 토스트·팝업 문구 미확보

**상황**
- Store 테스트에 넣을 토스트·중단 팝업 문구를 수집하려고 Figma MCP를 재호출했다.

**문제**
- 세션 초반에는 수집이 됐지만, 도중 Figma Desktop의 활성 탭이 바뀌어 "No node could be found" 오류로 토스트 2종·중단 팝업 문구를 확보하지 못했다.

**원인**
- figma-desktop MCP는 활성 탭의 문서만 조회할 수 있는데, 작업 중 대상 문서가 활성 탭에서 벗어났다.

**해결**
- 확보한 명세(FR 설명)와 화면 문구 기준으로 임시 문구를 상수로 지정하고 진행: 성공 토스트 "[콘서트명] 관심 콘서트로 등록되었어요", 실패 토스트 "관심 콘서트 등록에 실패했어요", 중단 팝업 "관심 콘서트 등록을 그만할까요?" / "지금은 그만할래요" / "잘못 눌렀어요". Figma 재접속 후 대조·교정 필요.

**교훈**
- Figma 수집이 필요한 문구는 세션 초반에 화면·토스트·팝업까지 한 번에 수집해 둔다.

### 2026-07-08 11:20 - 계획 문서에 Figma 링크 기재 지적

**상황**
- 계획 문서 배경에 근거 자료로 Figma 파일 URL(파일 키 포함)을 그대로 기재했다.

**문제**
- 사용자가 계획 문서에 MCP(Figma) 링크를 넣으면 안 된다고 지적했다. 저장소에 커밋되는 문서에 내부 디자인 파일 키가 노출된다.

**원인**
- 커밋 대상 문서와 세션 내부 참조를 구분하지 않고 URL을 그대로 옮겼다.

**해결**
- 계획 문서에서 URL을 제거하고 "Figma 디자인 문서(FR-01~06)"로만 표기했다.

**교훈**
- 저장소에 커밋되는 문서(plans/troubleshooting 등)에는 Figma URL·파일 키·노드 ID 같은 내부 링크를 넣지 않는다. 필요한 참조는 명세 이름(FR 번호)으로 표기한다.
