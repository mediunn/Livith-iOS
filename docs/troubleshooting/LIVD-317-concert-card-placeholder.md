## 기록

### 2026-11-07 - 검색 상태 변경의 send 단일 진입점

**상황**
- 사용자가 상태 변경은 내부 Intent를 send로 전달하는 MVI 구조여야 한다고 지적.

**문제**
- 초기 수정은 MainActor 격리만 추가하고 비동기 헬퍼의 직접적인 state 변경을 남김.
- 결과를 Result<SearchResult, SearchError>로 전달할 때 일반 catch의 any Error 추론으로 컴파일 실패.

**원인**
- 스레드 경고 해소에 집중해 상태 변경 진입점 규칙을 함께 적용하지 않음.

**해결**
- 디바운스 완료·다음 페이지 대기 완료·검색 성공/실패를 내부 Intent로 전달.
- state 변경은 send 안으로 모으고, 비동기 헬퍼는 대기와 조회 및 결과 전달만 수행.
- MainActor는 UI Store의 실행 격리로 유지. 기존 검색 결과 교체·페이지 추가·오류 처리 보호 테스트 후 구조 정리.
- do throws(SearchError)로 저장소의 typed throws 계약을 명시해 catch의 오류 타입 보존.
- 수정 후 디바운스·페이지 추가·페이지 조회 실패의 3개 회귀 테스트 통과. 모든 상태 발행이 메인 스레드이며 결과 교체·추가·오류 처리 유지 확인. 앱 전체 빌드 성공.

**교훈**
- 실행 스레드 격리와 MVI의 상태 변경 진입점은 각각 확인한다.
- 승격 후보: no

### 2026-11-07 - 검색 디바운스 상태의 백그라운드 발행

**상황**
- 사용자가 SearchStore.swift:120의 백그라운드 상태 발행 경고를 보고.

**문제**
- 검색 디바운스 이후 @Published state 변경이 메인 스레드 밖에서 발생.

**원인**
- send만 MainActor로 격리되어 있고, 비격리 헬퍼가 생성한 Task에서 대기 후 상태를 변경.

**해결**
- 수정 전 디바운스 상태의 백그라운드 발행을 테스트 실패로 재현. Store 전체 MainActor 격리 후 기존 2개 테스트 통과.
- 사용자 피드백에 따라 상태 변경도 send로 모으는 후속 구조 정리 완료. 3개 회귀 테스트 통과.
- SearchFeature에 테스트 타깃이 없어 기존 프로젝트 규칙으로 SearchFeatureTests 추가.
- 첫 실행은 테스트 소스 경로가 Sources로 연결되어 0건 실행됨. Tests 경로 매핑을 추가하고 실제 재현 테스트를 다시 실행.

**교훈**
- UI Store의 진입 메서드만 메인 액터로 지정해도 비격리 헬퍼가 만든 비동기 작업은 보호되지 않는다.
- 승격 후보: no

### 2026-11-07 - 모달 사용처의 후행 클로저 보존

**상황**

**문제**
- 변경 검토에서 취향 수정 화면 두 곳의 취소 클로저가 새 modifier 뒤에 붙은 것을 발견.

**원인**
- 생성자 괄호만 기준으로 modifier를 삽입해 후행 클로저 범위를 놓침.

**해결**
- 기존 취소 클로저까지 닫은 다음 여백·배치 modifier를 적용하도록 수정. 콜백 내용은 보존.
- 프로젝트 생성·앱 전체 빌드 성공. 이전·수정 모달 소스를 사용하는 시뮬레이터 앱에서 확인 2상태·신고 4상태의 픽셀 차이 0 확인.
- 키보드 높이 300을 가정한 회피 및 201자 초과 안내 표시·200자 안내 해제 확인. 실제 키보드 표시와 버튼·배경 탭은 수동 확인 대기.

**교훈**
- View 생성자에 modifier를 추가할 때 후행 클로저까지 포함한 표현식 경계를 확인한다.
- 승격 후보: no

### 2026-11-07 - 스크롤 상단 고정 간격

**상황**
- 사용자가 그리드 위 20 여백은 스크롤 중에도 위 요소와 붙지 않게 하려는 의도라고 설명.

**문제**
- 위 여백을 scrollContent의 contentMargins로 이동해 스크롤 중 사라질 수 있도록 구현.

**원인**
- 스크롤 영역 밖의 고정 간격과 스크롤 콘텐츠 내부 여백의 의도를 구분하지 못함.

**해결**
- 위 20은 사용하는 화면의 스크롤 영역 바깥 여백으로 지정.
- 화면에 있던 위 간격과 합쳐 설정 화면 32, 수동 검색 화면 29로 선언. 로딩 상태의 기존 간격은 각각 12, 9 유지.
- 아래 210만 스크롤 콘텐츠 여백으로 유지해 마지막 카드가 하단 버튼에 가리지 않도록 함.
- HomeFeature 빌드 성공. 실제 그리드 소스를 사용하는 시뮬레이터 앱에서 기존 최대 스크롤 거리 954와 수정 후 954 일치 확인. 빈 결과의 하단 인셋은 0이며 불필요한 스크롤이 없음.

**교훈**
- 위 요소와의 간격을 스크롤 중에도 유지해야 한다면 스크롤 영역 바깥에서 지정한다.
- 승격 후보: no

### 2026-11-07 - 화면 공통 여백 선언 통합

**상황**
- 사용자가 MD 상세처럼 같은 좌우 여백을 부모 VStack에서 한 번 선언할 수 있다고 지적.

**문제**
- 네비게이션 바의 내부 여백을 제거한 뒤 일부 화면의 동일한 외부 여백을 개별 자식에 반복 선언.

**원인**
- 호출부별 여백 이전에 집중하고 화면의 공통 부모까지 충분히 정리하지 않음.

**해결**
- MD 상세·추천 콘서트·약관·탈퇴 화면에서 부모의 좌우 16 여백으로 통합.
- 정보 제보는 네비게이션 바와 스크롤을 포함하는 부모에 통합하고, 전체 폭 그라데이션을 가진 하단 버튼은 별도 유지.
- 약관 목록의 기존 20 여백은 공통 16과 추가 4로 유지. 전체 폭 포스터·구분선·가로 스크롤이 있는 화면은 일괄 축소하지 않음.

**교훈**
- 외부 여백을 사용하는 화면으로 옮길 때 동일한 여백을 공유하는 부모까지 확인한다.
- 승격 후보: no

### 2026-11-07 - 네비게이션 바 외부 여백 이동 검증

**상황**
- 사용자가 같은 브랜치에서 네비게이션 바의 좌우 여백을 사용하는 화면으로 이동하도록 요청.

**문제**
- 변경 전후 PNG 파일의 바이트가 달라 픽셀 비교가 필요했으며, 임시 비교 스크립트의 이미지 초기화 API가 컴파일되지 않음.

**원인**
- PNG 파일 자체의 일치는 렌더링 일치와 다름. NSBitmapImageRep에 없는 초기화 메서드를 사용.

**해결**
- Data 기반 초기화로 임시 비교 스크립트 수정 후 실제 픽셀 비교.
- 네 가지 형태의 변경 전후 크기는 1170×774로 동일. 제목과 우측 버튼 영역의 픽셀은 동일하며 이미지 에셋 가장자리의 렌더링 차이는 육안으로 확인.
- 앱 전체 빌드 성공. 좌우 여백은 사용하는 화면으로 이동하고 높이·상하 간격은 유지.

**교훈**
- 화면 배치 유지 여부는 PNG 메타데이터를 제외하고 비교한다.
- 승격 후보: no

### 2026-11-07 - 탐색 카드 대체 이미지 미표시

**상황**
- 사용자가 탐색 화면의 카드 포스터 영역이 비어 있는 스크린샷을 제공.

**문제**
- 빌드 검증 후에도 실제 화면에서 대체 이미지가 보이지 않음.

**원인**
- 웹 SVG는 투명 배경이며 웹 카드의 CSS 배경색과 합쳐야 의도한 명암이 나타남. SVG만 추가한 iOS에서는 배경색이 빠져 패턴이 거의 보이지 않음.
- AsyncImageView는 URL이 있는 동안 KFImage 로딩 placeholder를 설정하지 않아 이미지 로딩 중 빈 영역이 나타남.

**해결**
- WebKit에서 웹 SVG와 실제 카드 배경색을 합성하여 1x·2x·3x PNG 에셋 생성.
- LivithCard에서 대체 이미지를 원격 이미지 아래에 배치하여 URL 없음·로딩 중·실패에도 항상 표시. 성공하면 원격 이미지가 덮음.
- 실제 디자인 시스템을 불러오는 임시 시뮬레이터 앱으로 네 상태의 렌더링 확인.
- `tuist build LivithDesignSystem`, `tuist build Livith-iOS-Dev` 성공.
- 시뮬레이터 접근과 로컬 검증 서버 실행은 샌드박스 권한 때문에 권한 확장 후 진행.

**교훈**
- 투명한 웹 에셋을 이식할 때 CSS 배경색을 함께 확인한다. 빌드 성공과 화면 렌더링 검증을 구분한다.
- 승격 후보: no
