# LIVD-427 인스타그램 공유 관심 콘서트 (archive)

## 결과
- 인스타 딥링크로 매칭 확인·직접 검색 후 관심 콘서트를 등록하는 앱 내 플로우를 구현했다. Share Extension과 매칭 API는 스텁·후속으로 남겼다.

## 남긴 결정
- 매칭 공급은 Domain 프로토콜과 UserData 스텁이다. API 확정 전에 화면을 먼저 둔다.
- 직접 찾기는 기존 다중 선택 화면을 확장하지 않고 단일 선택 Store를 새로 둔다.
- 정보 요청 버튼 노출은 포함하고, 요청 페이지와 툴팁은 후속이다.
- Share Extension과 공유 진입 화면은 제외하고 `livith://instagram`만 준비한다.
- 홈 화면은 수정하지 않고, 등록 성공은 기존 홈 위 토스트로 끝낸다.
- 딥링크 시뮬레이터 수동 확인은 하지 못했다.

## 컴파운딩
- rules 반영:
  - `project-operations.md` — 테스트 실패 시 diff로 선행 실패를 구분하고 이번 브랜치에서 고치지 않음
  - `security.md` — 커밋 대상 문서에 Figma URL, 파일 키, 노드 ID 금지
- 분리 확인으로 보류: 없음
- archive만 유지:
  - 신규 화면은 design context로 폰트·색·간격 표를 만든 뒤 재대조
  - 화면 변형의 헤더와 네비는 노드 단위로 대조. 화면을 범위에서 빼면 진입 버튼까지 빠지는지 확인
  - 같은 종류 토스트도 화면별 카피가 다를 수 있음
  - Figma 문구는 세션 초반에 화면·토스트·팝업을 한 번에 수집
- 반영 없음 / 사유: 디자인 대조 절차는 대상 규칙 파일이 없어 archive만 유지

## 교훈
- [스크린샷과 좌표만 보고 구현] → 신규 화면은 design context로 폰트·색·간격 표를 만들고 구현 후 재대조한다.
- [헤더를 두 화면이 같다고 가정] → 변형 화면의 헤더와 네비는 노드 단위로 대조하고, 제외한 화면의 진입 버튼이 같이 빠지는지 확인한다.
- [성공 토스트를 한 문구로 통일] → 화면마다 Figma 카피를 따로 확인한다.
- [전체 스위트 실패 1건] → diff와 대조해 선행 실패인지 먼저 가른다.
- [작업 중 Figma 활성 탭이 바뀜] → 필요한 문구는 세션 초반에 한 번에 수집한다.
- [계획 문서에 Figma URL 기재] → 커밋 문서에는 명세 이름만 적는다.
