### 2026-07-22 - FR-04 매칭 결과 화면에서 "직접 찾아볼게요"가 하단으로 밀리는 회귀

**상황**
- 서버 매칭이 실제로 성공(MATCHED 1건)하면서 처음으로 FR-04 결과 화면이 실기동으로 확인됐고, 유저가 "직접 찾아볼게요" 버튼이 화면 맨 아래(취소/등록 아래)에 있다고 지적했다.

**문제**
- 카드 채움 전환에서 3열 폭 유지용 빈 칸으로 넣은 `Color.clear.frame(maxWidth: .infinity)`가 세로로도 무한 확장되어, 카드 HStack이 남은 세로 공간을 전부 차지하며 아래 요소를 밀어냈다. 매칭 3개(빈 칸 없음)와 로딩 상태에서는 재현되지 않아 놓쳤다.

**원인**
- `Color`는 제안된 크기를 모두 채우는 뷰라 폭만 제한하면 높이는 무한 확장된다.

**해결**
- 빈 칸에 `.frame(height: 0)`을 추가해 폭 분할 역할만 하도록 수정. 실기동 재현(히게단 실게시물 MATCHED 1건)으로 "직접 찾아볼게요"가 카드 아래 30pt 규칙 위치(y 558)로 복원됨을 확인.

**교훈**
- 스페이서 용도의 `Color.clear`는 확장 축을 명시적으로 제한한다. 분기 상태(1·2·3개)별로 실기동 확인 범위를 나눠서 검증한다.

### 2026-07-22 - 관심 콘서트 등록 API가 구 스펙(body 방식)으로 남아있던 문제 → v7 정합

**상황**
- 유저가 등록하기 버튼을 "유저의 관심 콘서트 단건 추가" 명세(`POST /api/v7/users/interest-concert/{id}`)로 연결하고, 기존 구현이 있으면 재활용하라고 지시했다.

**문제**
- Store 흐름(선택→checkInterestedConcert→updateInterestedConcert)은 이미 재활용 구조였으나, `HomeAPI.updateInterestedConcert`가 구 스펙(`POST /users/interest-concert` + body `{concertId}`)이었고, 응답 DTO가 명세상 null 허용 필드(code/title/startDate/endDate/poster/venue)를 non-optional로 선언해 null 응답 시 디코딩이 깨질 수 있었다. `daysLeft` 필드도 누락.

**원인**
- LIVD-422에서 path variable 방식으로 바꿨다는 계획 문서가 있으나 해당 작업이 이 브랜치·develop에 반영되지 않은 상태였다(문서만 untracked로 존재).

**해결**
- TDD(red 3건 → green): 경로를 path variable + body 제거로 변경, 미사용 Request DTO 삭제, 응답 DTO를 명세 필수/optional에 맞게 조정(daysLeft 추가), `UserMapper`를 optional 대응으로 수정(daysLeft는 응답 값 우선, 없으면 startDate로 계산). LivithNetworking 130/130·UserData 40/40 통과.
- 실기동 E2E: FR-05에서 카드 선택→등록하기→v7 실서버 등록 성공, 홈 관심 콘서트 섹션에 즉시 반영 확인.

**교훈**
- "이미 구현됨"으로 기록된 API도 명세 페이지와 경로·필수/optional까지 재대조한다. 계획 문서의 [x]가 코드 반영을 보장하지 않는다.

**문제**

**교훈**
- 디자인 수치는 절대값이 아니라 제약(고정 여백·간격 vs 유동 폭)으로 해석해야 다른 화면 폭에서도 디자인 의도가 유지된다.

### 2026-07-21 - 툴팁 화살표 위치 피드백(메타데이터≠렌더) 및 로딩 dots 모션 명세 반영

**상황**

**문제**
- ① Figma 메타데이터의 Polygon 좌표(x=343..356, 말풍선 우측에서 5pt)를 기준으로 구현했으나, 실제 Figma 렌더 픽셀 실측은 화살표 중심이 말풍선 우측 끝에서 25pt였다. 메타데이터 노드 좌표와 렌더 결과가 달랐다.
- ② dots는 정적 원 3개로만 구현되어 있었다.

**원인**
- 메타데이터의 벡터 노드 좌표는 인스턴스 변환이 반영되지 않아 렌더와 어긋날 수 있는데 이를 신뢰했다.

**해결**

**교훈**
- 위치 검증의 최종 기준은 메타데이터 좌표가 아니라 렌더 픽셀이다. 모션 명세는 키프레임 수치를 코드 상수로 그대로 옮겨 결정적으로 구현한다.

### 2026-07-21 - 카드 이미지 크기 확인 요청·등록하기 비활성 색 불일치 피드백

**상황**
- 유저가 ① 콘서트 카드 이미지가 작아 보인다며 기존 컴포넌트 사용 여부를 물었고, ② 등록하기 비활성 버튼 색이 Figma와 다르다고 지적했다.

**문제**
- ① 픽셀 실측 결과 카드 포스터는 실기기·Figma 모두 108×158로 동일했고 `LivithCard` 컴포넌트를 그대로 사용 중 — 이전에 보낸 비교 이미지의 좌우 크롭 배율 차이(254pt vs 222pt 구간을 같은 폭으로 축소)로 작아 보인 것. 실제 불일치 아님.

**교훈**

### 2026-07-21 - 툴팁 시각 차이·하단 그라데이션 미구현 피드백 → 픽셀 재대조 반영

**상황**

**문제**
- ① 툴팁 텍스트가 Figma 렌더 대비 1.2배 큼(잉크 폭 102 vs 84pt): 토큰 표기는 Caption1(12)이지만 Figma 실제 렌더는 10pt 상당. ② 화살표가 날카로운 직선 삼각형(디자인은 둥근 꼭짓점). ③ 하단 152pt 투명→black100 그라데이션(버튼 상단 50pt 위 시작) 미구현 — 스크롤 콘텐츠가 버튼 아래로 그대로 노출.

**교훈**

### 2026-07-20 - 실기동(sim-use) 픽셀 실측에서 정적 코드 대조가 놓친 불일치 6건 발견

**상황**
- 유저 지시로 시뮬레이터 실기동 화면을 Figma와 픽셀 단위(3x 스크린샷 + 접근성 프레임)로 대조했다. 이전 검증은 코드-디자인 정적 대조(100%)였다.

**문제**
- 실기기(402pt)에서만 드러나는 불일치 6건: ① 그리드 행간 12(디자인 24) ② 카드 사이드 마진 20(flexible 셀 중앙 배치, 디자인 16 고정) ③ 검색필드 상단 30(디자인 32) ④ 검색필드→그리드 32(디자인 29) ⑤ 툴팁 세로 오프셋 13(버튼-말풍선 관계 기준 7) ⑥ `LivithReportButton .info`가 텍스트 black80·무보더(디자인: 텍스트 black50 + 1px black90 보더 캡슐).

**원인**
- 정적 대조는 상수·토큰 수준만 비교해 flexible 그리드 셀의 런타임 배치, 컴포넌트 내부 스타일(보더 유무), 시각 기준(컨테이너 여백 vs 실제 렌더 여백) 차이를 잡지 못했다. 디자인 메타데이터의 여백 수치도 컴포넌트 내부 패딩 때문에 화면 실측과 달랐다.

**해결**
- 그리드 행간 24, 열 정렬 topLeading/top/topTrailing(사이드 16 고정), 검색필드 32, 그리드 상단 합 29, 툴팁 오프셋 7, `.info` variant 텍스트 black50+보더 black90으로 수정. 공유 컴포넌트(그리드·버튼) 변경은 사용처 전수 확인(`.info`는 해당 화면 단독, 그리드는 관심콘서트 설정 화면도 동일 디자인 규칙이라 정합 개선).

**교훈**
- 디자인 대조는 코드 상수 비교로 끝내지 않고 실기기 렌더 픽셀·프레임 실측까지 한다. 특히 flexible 레이아웃과 컴포넌트 내부 패딩은 런타임에서만 검증된다.

### 2026-07-20 - 1차 연동 완료 직후 서버 명세 개정 발견 → 동기 API로 재작업
