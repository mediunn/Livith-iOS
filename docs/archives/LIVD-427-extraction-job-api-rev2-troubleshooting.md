# [LIVD-427] 인스타 추출 및 콘서트 매칭 API 명세 개정 반영 (rev2) - 트러블슈팅

## 기록

### 2026-07-21 - FR-05 검색 포커스 시 안내문구 숨김 동작 제거 피드백

**상황**
- FR-05 검색 화면에서 검색바 포커스 시 상단 안내 타이틀을 숨기고 검색바를 위로 당기는 인터랙션이 구현되어 있었다.

**문제**
- 유저가 요청한 적 없는 동작이라고 지적했다. 디자인 정적 화면에도 없는 임의 추가 인터랙션이었다 (이전 FR-05 검증 리포트에서도 "정적 디자인엔 없는 인터랙션 추가"로 표기됐던 항목).

**원인**
- 초기 구현 시 키보드 노출 공간 확보를 명세 근거 없이 추측으로 추가했다.

**해결**
- 포커스 분기를 제거하고 안내 타이틀을 항상 노출, 검색필드 상단 패딩 32 고정.

**교훈**
- 디자인·명세에 없는 인터랙션은 추측으로 추가하지 않는다. 검증 리포트에서 "명세 외 추가"로 표시된 항목은 유지 여부를 유저에게 확인한다.

### 2026-07-20 - 실기동(sim-use) 픽셀 실측에서 정적 코드 대조가 놓친 불일치 6건 발견

**상황**
- 유저 지시로 시뮬레이터 실기동 화면을 Figma와 픽셀 단위(3x 스크린샷 + 접근성 프레임)로 대조했다. 이전 검증은 코드-디자인 정적 대조(100%)였다.

**문제**
- 실기기(402pt)에서만 드러나는 불일치 6건: ① 그리드 행간 12(디자인 24) ② 카드 사이드 마진 20(flexible 셀 중앙 배치, 디자인 16 고정) ③ 검색필드 상단 30(디자인 32) ④ 검색필드→그리드 32(디자인 29) ⑤ 툴팁 세로 오프셋 13(버튼-말풍선 관계 기준 7) ⑥ `LivithReportButton .info`가 텍스트 black80·무보더(디자인: 텍스트 black50 + 1px black90 보더 캡슐).

**원인**
- 정적 대조는 상수·토큰 수준만 비교해 flexible 그리드 셀의 런타임 배치, 컴포넌트 내부 스타일(보더 유무), 시각 기준(컨테이너 여백 vs 실제 렌더 여백) 차이를 잡지 못했다. 디자인 메타데이터의 여백 수치도 컴포넌트 내부 패딩 때문에 화면 실측과 달랐다.

**해결**
- 그리드 행간 24, 열 정렬 topLeading/top/topTrailing(사이드 16 고정), 검색필드 32, 그리드 상단 합 29, 툴팁 오프셋 7, `.info` variant 텍스트 black50+보더 black90으로 수정. 공유 컴포넌트(그리드·버튼) 변경은 사용처 전수 확인(`.info`는 해당 화면 단독, 그리드는 관심콘서트 설정 화면도 동일 디자인 규칙이라 정합 개선).

**교훈**
- 디자인 대조는 코드 상수 비교로 끝내지 않고 실기기 렌더 픽셀·프레임 실측까지 한다. 특히 flexible 레이아웃과 컴포넌트 내부 패딩은 런타임에서만 검증된다.

### 2026-07-20 - develop 머지 후 LivithNetworking 테스트 4건 선행 실패 (v6 하드코딩)

**상황**
- origin/develop 머지(DEBUG 스킴 v7 전환, LIVD-349 포함) 후 LivithNetworking 전체 테스트를 실행했다.

**문제**
- `NetworkConfigTests`(1건), `RequestBuilderTests`(2건), `TokenRefreshServiceTests`(1건)가 `/api/v6` 하드코딩 기대값으로 실패했다.

**원인**
- LIVD-349가 프로덕션 `NetworkConfig`만 v7로 바꾸고 테스트 기대값을 갱신하지 않았다 (develop 자체의 선행 실패, git log로 테스트 파일 미변경 확인).

**해결**
- 테스트 지원 타입 `TestAPIVersion`(#if DEBUG → api/v7, else api/v6)을 추가하고 4건의 기대값을 조건부 계산으로 교체. 128/128 통과 확인. 이번 작업이 v7 반영을 포함하므로 보고만 남기지 않고 수정했다.

**교훈**
- 전역 설정(버전 등) 변경 커밋은 해당 값을 단언하는 테스트를 함께 갱신해야 한다. 머지 직후 전체 스위트로 선행 실패를 먼저 분리한다.

### 2026-07-20 - 1차 연동 완료 직후 서버 명세 개정 발견 → 동기 API로 재작업

**상황**
- 잡 생성 + long-poll 2개 API 기준으로 1차 연동을 완료·아카이브한 직후, 유저가 공개 링크로 공유한 명세 문서를 재확인했다.

**문제**
- 명세가 당일 개정되어(2026-07-20 22:09) 있었다: 단일 동기 API(`POST /extraction-jobs` → `{result, concerts}`)로 통합, `jobId`/폴링/`PENDING`/`EXTRACTING` 폐기, concerts 필드 다수가 null 허용으로 변경.
- 1차 연동은 과거 세션 기록(7/11 열람본) 기준이라 개정 전 명세였다.

**원인**
- 명세 문서 접근 불가로 과거 기록에 의존했고, 그 사이 서버 설계가 변경되었다("새로 수정된 API" 코멘트 7/13, 응답 구조 확정 7/20).

**해결**
- 개정 명세 기준으로 rev2 계획을 세우고 DTO·Mapper·Repository를 TDD로 재작업. develop 머지로 DEBUG v7 전환 수용.

**교훈**
- 복원본으로 작업했다면 연동 마무리 전에 원본 명세의 최종 수정 일시를 반드시 재확인한다. 서버 "구현 여부 Done" 전의 명세는 개정 가능성을 전제한다.
