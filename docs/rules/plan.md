# 계획 문서

## Purpose
- 에이전트가 컨텍스트만으로 즉흥 개발하지 않고, 계획을 먼저 수립한 뒤 작업하도록 한다.
- 작업의 의도와 범위를 문서로 고정하여 에이전트 종류에 관계없이 동일한 방향으로 개발한다.
- 작업 종료 시 교훈을 `docs/rules`로 환류하거나 압축 archive에 남겨 다음 사이클에 복리로 남긴다.

## Scope
- 단순 버그 수정이나 한두 파일 변경이 아닌, 계획이 필요한 작업에 적용한다.
- Claude Code, Cursor, Copilot 등 에이전트 종류에 관계없이 동일하게 적용한다.
- 이 저장소에서 plan 작성 여부·아카이브·컴파운딩의 정본은 이 문서다. `CLAUDE.md`와 문구가 다르면 이 문서를 따른다.
- 다음 용어는 이 문서에서 아래 의미로 사용한다.
- `계획 문서`: `docs/plans/LIVD-이슈번호-슬러그.md`
- `트러블슈팅 문서`: `docs/troubleshooting/LIVD-이슈번호-슬러그.md`
- `압축 archive`: `docs/archives/LIVD-이슈번호-슬러그.md` 단일 파일. 작업 중 plan·트러블슈팅을 합쳐 압축한 보관본
- `슬러그`: 파일명에서 이슈번호 다음 구간. 브랜치명 `type/LIVD-XXX-슬러그`의 설명부와 맞춘다
- `컴파운딩 게이트`: 교훈 분류 → rules 변경안·압축 archive 초안 제시 → 유저 승인 → 반영·저장·원본 제거
- `기능 완료 선언`: 유저가 해당 이슈의 구현이 끝났다고 명시한 발화. 예: 「완료」「다 됐어」「이슈 닫자」「머지해도 돼」「PR 올려」「아카이브해」「계획 종료」
- `기본 승격 규칙`: `plan.md`, `project-operations.md`, `git.md`, `tdd.md`, `code-convention.md`, `documentation.md`
- `분리 확인 규칙`: `architecture.md`, `security.md`

## Do
- 계획 문서는 `docs/plans/`에 작성한다.
- 파일명 형식: `LIVD-이슈번호-슬러그.md` (예: `LIVD-336-rules.md`).
- 계획 문서 작성 전에 `git branch --show-current`로 현재 브랜치명을 확인하고 이슈 번호와 슬러그를 확정한다.
- 계획 문서 양식은 `docs/templates/plan.md`를 따른다.
- 작업 항목은 체크박스(`- [ ]`)로 작성하고, 완료 시 체크(`- [x]`)한다.
- 작업 시작 전에 계획 문서를 유저에게 확인받는다.
- 작업 중 계획이 변경되면 계획 문서를 먼저 수정한 뒤 작업을 계속한다.
- 계획 문서의 검증 명령은 작업 환경에 맞게 조정하며, `docs/rules/project-operations.md`의 테스트 실행 규칙을 우선 따른다.
- 주석, MARK 섹션, 공백만 변경한 정리 작업은 직전 검증 결과를 유지하고 테스트를 반복 실행하지 않는다.

### 계획 필수·예외
- 다음 중 하나라도 해당하면 계획 문서를 작성하고 유저 확인 후에 코드를 변경한다.
  - Feature·Data·Core·Shared 중 모듈 2개 이상을 변경한다.
  - Domain 모델, Repository 계약, API(`NetworkEndpoint`) 계약을 변경한다.
  - 동작·데이터·보안·UX를 바꾸는 설계 선택이 아직 열려 있다.
- 입력이 짧아도 위 설계 선택이 남아 있으면 구현 전에 선택을 확정한다.
- 동일 패턴의 기계적 다파일 변경(리네임, import 정렬, 동일 한 줄 삽입)만이면 계획 문서 없이 진행할 수 있다.
- 한 모듈 안에서 레이어 경계를 넘지 않는 버그 수정·UI 배치만이면 계획 문서 없이 진행할 수 있다.

### 권한
- 계획 문서의 목표·불변조건·범위가 요구 동작의 정본이다.
- 작업 항목은 실행 순서와 분할만 담는다. 작업 항목과 정본이 충돌하면 정본을 따른다.
- 코드는 현재 구현 사실이며 원하는 동작의 증거가 아니다.
- 완료는 계획 문서 검증 칸의 명령 실행 결과로만 판정한다. 에이전트 요약만으로 완료 처리하지 않는다.

### 트러블슈팅
- 트러블슈팅 문서는 `docs/troubleshooting/`에 작성한다.
- 파일명 형식: 대응하는 계획 문서와 동일하게 `LIVD-이슈번호-슬러그.md`를 사용한다.
- 트러블슈팅 문서 양식은 `docs/templates/troubleshooting.md`를 따른다.
- 다음 상황이 발생하면 트러블슈팅 항목을 추가한다.
  - 에이전트가 작업을 시도했으나 실패한 경우
  - 유저로부터 결과물에 대한 수정 피드백을 받은 경우
  - 예상과 다른 동작이 발생하여 접근 방식을 변경한 경우
- 새 항목은 문서 상단에 추가한다 (최신순 정렬).

### 컴파운딩·아카이브
- `기능 완료 선언`이 있으면 `컴파운딩 게이트`를 실행한다.
- 유저가 「아카이브해」「이슈 닫자」「계획 종료」를 명시한 경우에도 `컴파운딩 게이트`를 실행한다.
- PR을 만들기 전에 해당 `슬러그`의 계획 문서·트러블슈팅 문서가 `docs/plans/`, `docs/troubleshooting/`에 남아 있으면 `컴파운딩 게이트`를 실행한다.
- PR을 만들기 전에 해당 `슬러그` 문서가 없으면 아카이브 단계만 통과로 본다.
- 아카이브 대상은 현재 브랜치·현재 계획과 `슬러그`가 일치하는 계획 문서와 동명 트러블슈팅 문서뿐이다.
- `LIVD-이슈번호-*` 전체를 일괄 아카이브하지 않는다.
- 대상이 애매하면 후보 목록을 유저에게 보여 고르게 한 뒤 진행한다.
- `컴파운딩 게이트` 순서: 교훈 분류 → `기본 승격 규칙` 변경안과 압축 archive 초안 작성 → 유저 승인 → 승인된 rules 반영 → `docs/templates/archive.md` 양식으로 `docs/archives/LIVD-이슈번호-슬러그.md` 저장 → 계획·트러블슈팅 원본 삭제.
- `분리 확인 규칙` 변경안이 있으면 `기본 승격 규칙` 변경안과 섞지 않고 분리해 제시하고, 유저가 따로 확인할 때까지 반영하지 않는다.
- rules 변경안이 없어도 압축 archive 초안에 대한 유저 승인을 받은 뒤에만 원본을 삭제한다.
- 교훈을 rules로 올릴 후보로 분류하는 조건은 다음을 모두 충족하는 경우다.
  - 다음 에이전트가 모르면 같은 실패가 난다.
  - 코드만 읽어서는 알기 어렵다.
  - 대상 규칙 파일에 같은 Do·Don't가 없다.
- 일회성 환경 이슈, 이번 이슈만의 디테일, 이미 rules에 있는 내용은 archive에만 남긴다.
- 압축 archive의 각 교훈은 `[원인 한 줄] → 교훈 한 줄` 형식으로 적는다.
- 아카이브 이후 같은 이슈의 추가 수정은 기본적으로 계획 문서 없이 진행한다.
- 아카이브 이후 추가 수정이 새 설계 선택이나 모듈 경계를 열면 후속 계획 문서를 작성한다.
- 후속 계획·트러블슈팅을 닫을 때는 기존 `압축 archive`에 追記 섹션으로 붙인다. 원본 계획·트러블슈팅을 되살리거나 압축본 전체를 처음부터 다시 쓰지 않는다.
- 기존 `docs/archives/`의 과거 문서를 새 양식으로 소급 변환하지 않는다.

## Don't
- 계획 문서 없이 계획 필수 조건에 해당하는 작업을 시작하지 않는다.
- 계획 문서에 없는 작업을 추가로 수행하지 않는다.
- 유저 확인 없이 계획을 변경하지 않는다.
- `docs/plans/`에 완료된 계획 문서를 방치하지 않는다.
- 트러블슈팅 내용을 계획 문서에 직접 작성하지 않는다.
- 유저 승인 없이 `docs/rules`를 컴파운딩으로 변경하지 않는다.
- 유저 승인 없이 계획·트러블슈팅 원본을 삭제하지 않는다.
- `슬러그`가 다른 동일 이슈 번호 문서를 함께 아카이브하지 않는다.
- `분리 확인 규칙` 변경을 `기본 승격 규칙` 변경과 한 묶음으로 승인·반영하지 않는다.
- 해당 `슬러그`의 계획·트러블슈팅이 `docs/plans/` 또는 `docs/troubleshooting/`에 남은 채로 PR을 만들지 않는다.

## Exception
- 계획 필수·예외에 적은 기계적 다파일 변경과 한 모듈·레이어 내부 버그·UI 배치는 계획 문서 없이 진행할 수 있다.
- 긴급 핫픽스는 계획 문서 없이 진행할 수 있다. 사후에 `압축 archive`를 남길 수 있다.
- 원래 계획·트러블슈팅이 없는 단순 작업은 컴파운딩 게이트를 건너뛴다.
- 유저가 이번 PR의 아카이브 보류를 명시한 경우에는 게이트를 건너뛰고, 보류 사유를 응답 또는 PR 본문에 남긴다.
- 한 번의 예외를 다른 이슈·다른 슬러그·다른 PR로 확장하지 않는다.

## Checklist
- 계획 필수 조건이면 `docs/plans/`에 계획 문서가 있고 유저가 확인했는가
- 정본(목표·불변조건)과 작업 항목이 충돌할 때 정본을 따랐는가
- 완료를 검증 명령 결과로만 판정했는가
- `기능 완료 선언` 또는 PR 전 잔여 문서가 있을 때 `컴파운딩 게이트`를 실행했는가
- 아카이브 대상이 `슬러그` 일치 문서만인가
- rules·압축 archive 반영 전에 유저 승인을 받았는가
- `분리 확인 규칙`을 기본 승격과 섞지 않았는가
- 저장본이 `docs/templates/archive.md` 양식의 단일 `압축 archive`인가
- 원본 계획·트러블슈팅을 승인과 저장 후에만 삭제했는가
- PR 전에 해당 `슬러그` 문서가 `plans/`·`troubleshooting/`에 없는가 (보류 예외 제외)
