# Test Driven Development

## Purpose
- 이 저장소에서 AI가 테스트 주도 개발을 일관된 방식으로 수행하기 위한 TDD 규칙을 정의한다.
- 요구사항을 작은 단위로 검증하고 회귀를 줄이며 변경 단위를 통제하기 위한 작업 기준을 고정한다.

## Scope
- 이 저장소에서 AI가 수행하는 도메인 로직, 매퍼, 스토어, 리듀서, 상태 변경 로직 작업에 적용한다.
- 순수 UI 배치 작업에는 적용하지 않는다.
- 다음 용어는 이 문서에서 아래 의미로 사용한다.
- `실패 테스트`: `생산 코드` 변경 전에 작성하고 컴파일에 성공한 뒤 실제 실행 결과로 실패를 확인한 테스트
- `생산 코드`: 테스트를 통과시키기 위해 수정하는 앱 코드
- `리팩터링`: 테스트 통과 상태를 유지한 채 구조만 정리하는 변경
- `보호 테스트`: 변경 대상 동작을 검증하고 현재 통과하고 있는 테스트
- `given-when-then 섹션`: 테스트 본문에 `// Given`, `// When`, `// Then` 주석을 둔 구조
- `SUT`: 현재 테스트가 직접 검증하는 단일 대상
- `테스트 더블`: mock, stub, spy처럼 실제 의존성을 대체하는 테스트용 대역
- `Testing 기반 테스트 타입`: `Testing` 프레임워크를 사용하는 테스트 타입
- `XCTest 기반 테스트 타입`: `XCTestCase`를 상속하는 테스트 타입
- `예외 허용 작업`: `실패 테스트`를 먼저 작성해도 `생산 코드` 변경 전에는 실제 실행으로 실패를 확인할 수 없는 연결 구간 작업
- 외부 SDK 콜백 연결, 시스템 delegate 연결, 상태 로직이 없는 UI 배선 작업은 `예외 허용 작업`에 포함된다.
- 서비스 장애 대응, 크래시 대응, 보안 이슈 대응은 그중 연결 구간 작업일 때만 `예외 허용 작업`에 포함된다.
- `TDD red 성립 불가`: `생산 코드`에 이미 변경 대상 동작이 구현되어 있어 `실패 테스트`를 새로 작성해도 처음 실행부터 통과하는 상태
- `추가 보호 테스트`: `TDD red 성립 불가` 상태에서 기존 동작을 검증하기 위해 추가하는 `보호 테스트`

## Do
- `생산 코드` 변경 전에는 해당 변경을 설명하는 `실패 테스트`를 먼저 작성한다.
- `실패 테스트`는 `생산 코드` 변경 전에 실제로 실행해 실패를 확인하고, 그 실패 원인이 기대한 동작 부재인지 검증한다.
- 새 타입, 새 메서드, 새 시그니처가 없어 테스트가 컴파일되지 않으면 테스트 컴파일에 필요한 최소 선언만 먼저 추가할 수 있다.
- 테스트 컴파일에 필요한 최소 선언에는 동작 구현을 넣지 않고, 추가한 뒤에는 해당 테스트를 다시 실행해 런타임 실패를 확인한다.
- 작업은 `red -> verify red -> green -> verify green -> refactor` 순서로 반복한다.
- `green` 단계에서는 현재 `실패 테스트`를 통과시키는 최소한의 `생산 코드`만 추가하거나 수정한다.
- `green` 단계 뒤에는 현재 `실패 테스트`와 영향 범위의 `보호 테스트`를 다시 실행해 통과와 회귀 여부를 확인한다.
- `refactor` 단계에서는 테스트가 통과한 상태에서만 구조를 정리한다.
- `refactor` 단계 뒤에는 변경 대상 동작을 보호하는 `보호 테스트`를 다시 실행해 통과를 확인한다.
- 순수 `리팩터링` 작업을 단독으로 진행할 때는 변경 대상 동작을 보호하는 `보호 테스트`가 먼저 통과하고 있어야 한다.
- `TDD red 성립 불가` 상태에서는 `실패 테스트`를 강제로 만들지 않고 `추가 보호 테스트`로 현재 동작을 검증한다.
- 프로덕션 Repository, Service, Store 생성자에 테스트 전용 클로저, 파라미터, 초기화 경로를 추가하지 않는다.
- Repository 단위 테스트를 작성하기 전에 Repository가 의존하는 객체가 protocol 또는 adapter로 추상화되어 있는지 확인한다.
- 테스트 헬퍼 함수의 기본 파라미터가 필요하면 optional 파라미터로 선언하고 함수 본문에서 기본값을 생성한다.
- 버그 수정 작업에서는 버그를 재현하는 `실패 테스트`를 먼저 작성한다.
- 테스트는 준비, 행동, 검증 순서가 드러나게 작성한다.
- 테스트 이름과 제목은 검증하는 단일 행동이 드러나게 작성한다.
- 준비 단계와 행동 단계와 검증 단계가 길거나 분리 필요성이 큰 테스트에서는 `given-when-then 섹션`을 사용한다.
- `given-when-then 섹션`을 사용하는 경우 `Given`에서는 `SUT`와 입력 조건을 준비한다.
- `given-when-then 섹션`을 사용하는 경우 `When`에서는 `SUT`에 단일 행동을 수행한다.
- `given-when-then 섹션`을 사용하는 경우 `Then`에서는 `SUT`의 결과와 부수효과를 검증한다.
- 테스트는 실제 동작과 실제 상태 변화 검증을 우선하고, `테스트 더블`은 불가피한 외부 의존성에서만 사용한다.
- 새 테스트 파일은 `Testing`을 우선 사용한다.
- 새 테스트 타입이 필요하면 새 테스트 파일을 만들고 `Testing 기반 테스트 타입`으로 작성한다.
- `Testing`의 `@Test("...")` 제목은 테스트가 검증하는 행동을 설명하는 한글 문장으로 작성하고 코드 식별자는 그대로 사용할 수 있다.
- `Testing`의 `@Suite("...")` 제목은 한글로 작성한다.

## Don't
- `실패 테스트` 없이 먼저 `생산 코드`를 작성하지 않는다.
- 컴파일 실패를 `red`로 처리하지 않는다.
- 컴파일 오류, 오타, 잘못된 테스트 설정으로 실패한 테스트를 올바른 `실패 테스트`로 간주하지 않는다.
- `red` 단계를 건너뛰고 바로 `green` 단계로 들어가지 않는다.
- 처음 실행에서 바로 통과한 테스트를 `red` 단계로 간주하지 않는다.
- 여러 행동을 한 테스트에 함께 넣지 않는다.
- 준비, 행동, 검증 순서가 드러나지 않는 테스트를 작성하지 않는다.
- `SUT`를 둘 이상 동시에 검증하는 테스트를 작성하지 않는다.
- 버그를 재현하는 `실패 테스트` 없이 버그를 바로 수정하지 않는다.
- `테스트 더블`의 호출 여부만 검증하고 `SUT`의 결과나 부수효과 검증을 생략하지 않는다.
- 수동 확인만으로 자동화 테스트를 대체하지 않는다.
- 기존 `XCTest` 테스트 파일에 새 테스트 타입을 추가하지 않는다.
- 기존 `XCTest 기반 테스트 타입`에 새 테스트 메서드를 추가하지 않는다.
- 기존 `XCTest` 테스트 파일을 수정한다는 이유만으로 그 파일 전체를 `Testing`으로 전환하지 않는다.
- 같은 테스트 함수 안에서는 `Testing`과 `XCTest` API를 혼용하지 않는다.
- 같은 테스트 타입 안에서는 `Testing`과 `XCTest` API를 혼용하지 않는다.
- `예외 허용 작업`이 아닌데도 TDD 예외로 처리하지 않는다.
- `TDD red 성립 불가` 상태에서 임의로 실패 조건을 추가해 `실패 테스트`를 작성하지 않는다.
- 프로덕션 코드의 생성자나 메서드 시그니처에 테스트 편의를 위한 파라미터를 추가하지 않는다.
- Repository의 네트워크 의존성을 추상화하지 않은 상태에서 Repository 단위 테스트를 작성하지 않는다.
- 테스트 헬퍼 함수의 기본 파라미터에 인스턴스 메서드, 인스턴스 프로퍼티를 사용하지 않는다.

## Exception
- `예외 허용 작업`에만 TDD 예외를 허용한다.
- 한 번의 예외를 다른 모듈, 다른 작업, 다른 테스트 파일로 확장하지 않는다.
- `예외 허용 작업`에서도 테스트 가능 구간이 생기면 그 시점부터 `red -> verify red -> green -> verify green -> refactor`를 다시 적용한다.
- TDD 예외를 사용한 경우에는 최종 보고에서 대상과 이유를 함께 적는다.
- `TDD red 성립 불가` 상태에서는 red 단계 없이 `추가 보호 테스트`를 먼저 작성할 수 있다.
- 프로덕션 객체에 테스트 전용 의존성을 추가하는 대신, 테스트 대상의 의존성을 protocol로 추상화하는 선행 작업을 수행할 수 있다.

## Checklist
- `생산 코드` 변경 전에 해당 변경을 설명하는 `실패 테스트`를 먼저 작성했는지 확인한다.
- `실패 테스트`를 `생산 코드` 변경 전에 컴파일에 성공한 상태로 실제 실행해 실패를 확인했고, 그 실패 원인이 기대한 동작 부재였는지 확인한다.
- 처음 실행에서 테스트가 바로 통과하지 않았는지 확인한다.
- 컴파일 실패를 `red`로 처리하지 않았는지 확인한다.
- 새 타입, 새 메서드, 새 시그니처가 없어 테스트가 컴파일되지 않을 때 테스트 컴파일에 필요한 최소 선언만 먼저 추가했는지 확인한다.
- 테스트 컴파일에 필요한 최소 선언에 동작 구현을 넣지 않았고, 추가한 뒤 해당 테스트를 다시 실행해 런타임 실패를 확인했는지 확인한다.
- 작업을 `red -> verify red -> green -> verify green -> refactor` 순서로 반복했는지 확인한다.
- `green` 단계에서 현재 `실패 테스트`를 통과시키는 최소한의 `생산 코드`만 추가하거나 수정했는지 확인한다.
- `green` 단계 뒤에 현재 `실패 테스트`와 영향 범위의 `보호 테스트`를 다시 실행해 통과와 회귀 여부를 확인했는지 확인한다.
- `refactor` 단계에서 테스트가 통과한 상태에서만 구조를 정리했는지 확인한다.
- `refactor` 단계 뒤에 변경 대상 동작을 보호하는 `보호 테스트`를 다시 실행해 통과를 확인했는지 확인한다.
- 순수 `리팩터링` 작업을 단독으로 진행할 때 변경 대상 동작을 보호하는 `보호 테스트`가 먼저 통과하고 있었는지 확인한다.
- 버그 수정 작업에서 버그를 재현하는 `실패 테스트`를 먼저 작성했는지 확인한다.
- 테스트가 준비, 행동, 검증 순서가 드러나게 작성됐는지 확인한다.
- 테스트 이름과 제목이 검증하는 단일 행동을 드러내는지 확인한다.
- 준비 단계와 행동 단계와 검증 단계가 길거나 분리 필요성이 큰 테스트에서 `given-when-then 섹션`을 사용했는지 확인한다.
- `given-when-then 섹션`을 사용하는 경우 `Given`에서 `SUT`와 입력 조건을 준비했는지 확인한다.
- `given-when-then 섹션`을 사용하는 경우 `When`에서 `SUT`에 단일 행동을 수행했는지 확인한다.
- `given-when-then 섹션`을 사용하는 경우 `Then`에서 `SUT`의 결과와 부수효과를 검증했는지 확인한다.
- 테스트가 가능하면 실제 동작과 실제 상태 변화를 검증하고, `테스트 더블`이 불가피한 외부 의존성에만 제한적으로 사용됐는지 확인한다.
- 새 테스트 파일에 `Testing`을 우선 사용했는지 확인한다.
- 새 테스트 타입이 필요할 때 새 테스트 파일을 만들고 `Testing 기반 테스트 타입`으로 작성했는지 확인한다.
- 기존 `XCTest` 테스트 파일에 새 테스트 타입을 추가하지 않았는지 확인한다.
- 기존 `XCTest 기반 테스트 타입`에 새 테스트 메서드를 추가하지 않았는지 확인한다.
- 기존 `XCTest` 테스트 파일을 수정한다는 이유만으로 그 파일 전체를 `Testing`으로 전환하지 않았는지 확인한다.
- `Testing`의 `@Test("...")` 제목을 테스트가 검증하는 행동을 설명하는 한글 문장으로 작성하고 코드 식별자를 그대로 사용했는지 확인한다.
- `Testing`의 `@Suite("...")` 제목을 한글로 작성했는지 확인한다.
- 같은 테스트 함수 안에서 `Testing`과 `XCTest` API를 혼용하지 않았는지 확인한다.
- 같은 테스트 타입 안에서 `Testing`과 `XCTest` API를 혼용하지 않았는지 확인한다.
- 수동 확인만으로 자동화 테스트를 대체하지 않았는지 확인한다.
- `예외 허용 작업`이 아닌데도 TDD 예외로 처리하지 않았는지 확인한다.
- `TDD red 성립 불가` 상태에서 무리한 실패 테스트를 만들지 않았는지 확인한다.
- 프로덕션 코드 생성자에 테스트 전용 파라미터가 추가되지 않았는지 확인한다.
- Repository 단위 테스트 전에 의존 객체가 추상화되어 있는지 확인한다.
- 테스트 헬퍼 기본 파라미터에 인스턴스 멤버가 사용되지 않았는지 확인한다.
