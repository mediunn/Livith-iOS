# Git

## Purpose
- 커밋 히스토리의 일관성을 유지하고, 변경 사유를 빠르게 파악하기 위해 사용한다.
- 브랜치 전략과 커밋 컨벤션을 통일하여 협업 충돌과 리뷰 비용을 줄인다.

## Scope
- 이 프로젝트의 모든 Git 작업(커밋, 브랜치, PR, 머지)에 적용한다.

## Do

### 브랜치
- `main`은 릴리즈 가능한 상태만 유지한다.
- `develop`은 다음 릴리즈를 위한 통합 브랜치로 사용한다.
- 모든 작업 브랜치는 `develop`에서 분기한다.
- 작업 브랜치는 `develop`으로 PR을 통해 머지한다.
- `develop`에서 `main`으로의 머지는 릴리즈 시점에만 수행한다.
- 작업 시작 전 `develop`에서 최신 코드를 pull 받는다.
- 충돌 발생 시 로컬에서 해결한 뒤 머지한다.

### 브랜치 네이밍
- 형식: `type/이슈키-간략한-설명`
- 이슈 키는 Linear 이슈 키를 사용한다 (예: `LIVD-123`).
- 설명은 영문 소문자와 하이픈(`-`)으로 작성한다.
- 허용 타입:

| 타입 | 용도 |
|------|------|
| `add` | 새로운 리소스, 에셋 추가 |
| `feat` | 새로운 기능 추가 |
| `fix` | 버그 수정 |
| `refactor` | 동작 변경 없는 구조 개선 |
| `style` | UI 리소스 변경 (이미지, 색상, 폰트) |
| `setting` | 프로젝트 설정, 환경 구성 |
| `hotfix` | 릴리즈 후 긴급 수정 |
| `chore` | 빌드, CI, 문서 등 코드 외 변경 |
| `test` | 테스트 코드 추가 또는 수정 |

- 예시: `feat/LIVD-10-network`, `fix/LIVD-237-amplitude`, `docs/LIVD-336-rules`

### 커밋 메시지
- 형식: `[Type] 이슈키 - 변경 내용 요약`
- 이슈 키는 Linear 이슈 키를 사용한다 (예: `LIVD-123`).
- 이슈 키와 변경 내용 사이 구분자는 반드시 ` - `를 사용한다.
- 이슈 키와 변경 내용 사이에 ` - ` 이외의 구분자는 사용하지 않는다.
- 변경 내용 요약은 한글로 작성한다.
- 한 줄로 작성하며, 50자 이내를 권장한다.
- 끝에 마침표를 붙이지 않는다.
- 커밋 타입과 실제 변경 내용을 일치시킨다.
- 최근 커밋에 다른 형식이 있어도 현재 문서의 커밋 메시지 형식을 우선한다.
- 커밋 전 변경 내용을 `git diff`로 확인한다.
- 좋은 예: `[Chore] LIVD-363 - 회원가입 계획 문서 추가`
- 나쁜 예: `[Chore] LIVD-363: 회원가입 계획 문서 추가`
- 나쁜 예: `[Chore] LIVD-363 / 회원가입 계획 문서 추가`

### 커밋 타입

| 타입 | 용도 | 예시 |
|------|------|------|
| `[Add]` | 새로운 리소스, 에셋 추가 | `[Add] LIVD-224 - 이미지 에셋 추가` |
| `[Feat]` | 새로운 기능 추가 | `[Feat] LIVD-223 - 마이페이지 트래킹 코드 삽입` |
| `[Fix]` | 버그 수정 | `[Fix] LIVD-231 - 7일 이내 탈퇴 회원 재가입 시 에러 처리 로직 수정` |
| `[Refactor]` | 동작 변경 없는 구조 개선 | `[Refactor] LIVD-231 - 불필요한 바인딩 변수 전달 제거` |
| `[Style]` | UI 리소스 변경 (이미지, 색상, 폰트) | `[Style] LIVD-231 - 로그인 화면 온보딩 이미지 교체` |
| `[Setting]` | 프로젝트 설정, 의존성 변경 | `[Setting] LIVD-223 - Concert Feature에 Amplitude 의존성 추가` |
| `[Hotfix]` | 릴리즈 후 긴급 수정 | `[Hotfix] 버전 1.0.1로 변경` |
| `[Merge]` | PR 머지 커밋 | `[Merge] LIVD-238 from fix/LIVD-237-amplitude` |
| `[Chore]` | 빌드, CI, 문서 등 코드 외 변경 | `[Chore] LIVD-336 - 규칙 문서 추가` |
| `[Test]` | 테스트 코드 추가 또는 수정 | `[Test] LIVD-50 - 로그인 Store 단위 테스트 추가` |

### 커밋 단위
- 하나의 커밋은 하나의 논리적 변경만 포함한다.
- 기능 추가와 리팩터링을 같은 커밋에 섞지 않는다.
- 동작하는 상태에서만 커밋한다 (빌드가 깨지는 커밋을 남기지 않는다).

### Hotfix
- `main` 브랜치에서 직접 작업하거나, `hotfix/설명` 브랜치를 사용한다.
- 수정 후 `main`과 `develop` 양쪽에 반영한다.

### Pull Request
- PR 제목 형식: `[Type] 작업 설명` (예: `[Fix] 위젯 관련 코드 삭제 및 크래시 수정`)
- PR 제목에 이슈 키를 포함하지 않는다.
- PR 본문에는 변경 사유와 주요 변경 사항을 작성한다.
- 관련 이슈 키를 본문에 명시한다 (예: `Resolved: LIVD-123`).
- 리뷰어를 최소 1명 지정한다.
- 머지 커밋 메시지 형식: `[Merge] 이슈키 from 브랜치명`
- Squash Merge는 사용하지 않는다 (커밋 히스토리를 보존한다).
- 머지 후 원격 작업 브랜치를 삭제한다.

## Don't
- `main` 브랜치에 직접 push하지 않는다 (Hotfix 제외).
- `develop` 브랜치에 직접 push하지 않는다.
- `git push --force`를 공유 브랜치(`main`, `develop`)에 사용하지 않는다.
- 커밋 메시지에서 이슈 키와 변경 내용 사이에 ` - ` 이외의 구분자를 사용하지 않는다.
- 최근 커밋 스타일을 이유로 현재 규칙과 다른 커밋 메시지 형식을 따르지 않는다.
- 하나의 커밋에 서로 다른 타입의 변경을 섞지 않는다.
- 이슈와 무관한 변경을 작업 브랜치에 포함하지 않는다.
- 빌드가 깨지는 상태로 커밋하지 않는다.
- 커밋 메시지에 `Co-Authored-By`를 넣지 않는다.

## Exception
- `[Hotfix]`는 `main`과 `develop`에서 직접 작업할 수 있다.
- `[Hotfix]`는 이슈 키 없이 커밋할 수 있다.
- 초기 프로젝트 설정 등 이슈가 없는 경우 이슈 키를 생략할 수 있다.
- 긴급 상황에서 리뷰어 없이 머지할 수 있으나, 사후 리뷰를 반드시 진행한다.

## Checklist
- 커밋 메시지가 `[Type] 이슈키 - 설명` 형식을 따르는가
- 이슈 키와 설명 사이 구분자가 ` - `인가
- 최근 커밋이 아니라 현재 규칙 문서를 기준으로 메시지를 작성했는가
- 커밋 타입이 변경 내용과 일치하는가
- 하나의 커밋에 하나의 논리적 변경만 포함되어 있는가
- 브랜치 이름이 `type/이슈키-설명` 형식을 따르는가
- PR 제목과 본문이 작성 규칙을 따르는가
- 머지 후 원격 작업 브랜치를 삭제했는가
