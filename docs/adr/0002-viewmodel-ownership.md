# ADR 0002: 상태와 작업 수명에 따른 ViewModel 경계

## 상태

승인 — 2026-11-26. [이슈 #341](https://github.com/mediunn/Livith-iOS/issues/341)부터 iOS에서 ViewModel로 전환하기로 한 기능에 적용한다.

## 배경

공연 요청, 관심 콘서트 목록, 관심 콘서트 설정에서는 각각 화면이 ViewModel을 소유했다. 인스타그램 수동 공연 검색에서는 여러 카드와 등록 버튼이 하나의 선택을 공유한다. 이 기능을 옮길 때 화면이나 셀의 개수만으로 모델을 나누면, 누가 선택을 바꿀 수 있는지와 누가 진행 중인 요청을 취소할지가 모호해진다.

## 검토한 대안

| 경계 | 장점 | 비용 |
| --- | --- | --- |
| 화면마다 ViewModel 하나 | 화면의 진입과 종료에 맞춰 상태를 관리하기 쉽다. | 항목별 작업까지 화면이 관리하면 개별 요청의 진행 상태와 취소 처리가 한곳에 모인다. |
| 재사용하는 셀마다 ViewModel 하나 | 항목별로 독립적인 작업을 테스트하기 쉽다. | 여러 셀이 공유하는 선택까지 복제하면 셀 사이에 동기화가 필요하다. |
| 함께 바뀌는 상태와 작업 수명에 따라 소유자 결정 | 공유 선택은 한곳에서 바꾸고 항목별 작업은 독립적으로 다룰 수 있다. | 화면을 떠나거나 셀이 사라질 때 어떤 상태와 작업을 유지할지 판단해야 한다. |

## 결정과 이유

함께 바뀌어야 하는 상태는 그 변경을 조정할 수 있는 가장 가까운 공통 소유자에 둔다. #341에서는 목록이 `selectedConcertID` 하나를 소유한다. 다른 카드를 누르면 ID를 교체하고 같은 카드를 다시 누르면 선택을 해제한다. 카드의 선택 표시와 등록 버튼의 활성 여부는 이 값에서 정한다. 카드는 표시할 값과 탭 콜백만 받으면 된다.

셀에 독립적인 상태 전이나 비동기 작업이 있다면 셀 단위 ViewModel을 둘 수 있다. 예를 들어 항목별 미리듣기에 취소와 재시도가 있다면, 스크롤로 셀이 사라질 때 재생을 끝낼지 먼저 정한다. 사라진 뒤에도 작업을 이어가야 한다면 목록 등 더 오래 살아 있는 소유자가 항목 ID로 모델이나 작업을 보관한다.

## 영향·트레이드오프

기존 Store에는 MVI 규칙을 계속 적용한다. 전환 대상에서는 화면·목록·셀 중 상태를 변경할 곳과 작업을 끝낼 시점을 정해야 한다. #341의 단일 선택은 카드를 새로 만들거나 검색 결과의 순서가 바뀌어도 같은 공연 ID를 기준으로 검증할 수 있다.
